# SELLFORM MVP — версия 2.4.0

Стартовый проект B2B-платформы услуг для селлеров маркетплейсов. Бизнес-модель: собственное агентство SELLFORM, независимые исполнители и партнёрские агентства.

## Стек
- Next.js 15 App Router + TypeScript
- Supabase Auth (`@supabase/ssr`)
- PostgreSQL / Supabase RLS и транзакционные RPC
- Supabase Storage (приватный bucket; серверная загрузка через service-role adapter)
- Zod для валидации API
- Node.js test runner для проверок ролевых переходов

## Реализовано (v2.4.0)
- Ограничена видимость полной финансовой разбивки: только селлер-владелец заказа, ответственное агентство и ADMIN; исполнители читают только собственные проводки.
- RPC финансового закрытия использует безопасный пустой `search_path` и проверяет ответственное агентство/ADMIN.
- API загрузки файлов не раскрывает клиенту сырые сообщения Supabase Storage/PostgreSQL.
- Регистрация и вход по email/password с выбором роли селлера, агентства или независимого исполнителя; ADMIN не доступен через публичную регистрацию.
- Роли профилей: `SELLER`, `AGENCY`, `FREELANCER`, `ADMIN`.
- Создание и просмотр заказов.
- Типы услуг: дизайн карточки, инфографика, контент/SEO, полный пакет.
- Принятие свободного заказа агентством.
- Назначение исполнителя и история статусов.
- Ролевой экран `/workspace` для селлера, агентства, исполнителя и администратора.
- Серверный middleware для обновления Auth cookies и перенаправления неавторизованных пользователей с защищённых страниц.
- Транзакционные RPC для claim/status/assignment; прямые клиентские UPDATE/INSERT на критические таблицы ограничены миграцией `0003`.
- Рабочие действия в карточке заказа: агентство принимает свободную заявку, участники меняют статус в рамках ролевых правил, агентство назначает фрилансера или партнёрское агентство. Повторно назначенные участники исключаются из кандидатов; история назначений показывает имена, тип участия, сумму и дату.
- Загрузка вложений к заказам с проверкой расширения, MIME-типа и сигнатуры содержимого в приватный Supabase Storage: PDF, изображения, документы Office, TXT и ZIP до 20 МБ; прямой Storage INSERT для пользовательских JWT закрыт, загрузка выполняется серверным service-role адаптером после проверки участника; метаданные регистрируются транзакционной RPC.
- Типы файлов заказа: техническое задание (`BRIEF`), исходный материал (`REFERENCE`) и готовый результат (`DELIVERABLE`); права на тип файла проверяются в API и PostgreSQL.
- Сдача результата на QA разрешена только после загрузки нового `DELIVERABLE`; после запроса доработки старый результат не позволяет повторно отправить заказ на проверку.
- Явные переходы процесса: агентство переводит заказ из согласования в работу и затем в QA; фрилансер/партнёрское агентство отправляет только назначенную ему работу; селлер принимает результат или возвращает его на доработку.
- Каталог исполнителей и партнёрских агентств: профили, специализации, портфолио, ценовой диапазон, доступность, публикация и фильтрация.
- Рейтинг и отзывы: клиент или ответственное агентство может оценить назначенного внешнего исполнителя после завершения заказа; повторная оценка по тому же заказу блокируется на уровне БД.
- Финансовый контур: условия заказа (стоимость клиента, сумма исполнителю, комиссия SELLFORM и доход агентства), неизменяемые после начисления проводки, финансовый кабинет `/finance`.
- Административная панель `/admin`: сводка аккаунтов, заказов и внутренних начислений, последние заказы и новые профили. Доступ только для роли `ADMIN`.
- Модерация каталога в `/admin`: одобрение/отклонение профилей исполнителей и агентств, комментарии владельцу и журнал решений. Публично видны только одобренные профили; изменение публичных данных отправляет профиль на повторную проверку.

- Все функции `SECURITY DEFINER` дополнительно закреплены на пустом `search_path` миграцией `0018_security_definer_search_path_hardening.sql`; прикладные таблицы и схемы в этих функциях должны быть указаны с явной схемой.

## Запуск
1. Node.js 20+.
2. `npm install`.
3. Создать проект Supabase.
4. Скопировать `.env.example` в `.env.local`, заполнить `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
5. Выполнить SQL-миграции строго по порядку: `0001_initial.sql`–`0018_security_definer_search_path_hardening.sql`. Для существующей базы сначала проверить, какие миграции уже применены, и выполнить только отсутствующие.
6. Заполнить `SUPABASE_SERVICE_ROLE_KEY` только в серверном `.env.local` и в Vercel Environment Variables (Production/Preview, если загрузка нужна там). Ключ доступен только серверному API и не должен попадать в GitHub или `NEXT_PUBLIC_*`.
7. `npm run dev`, затем открыть `http://localhost:3000`.

## Важные ограничения текущей версии
- Это MVP-каркас, а не production-ready сервис.
- Административная панель включает обзор показателей, очередь модерации каталога и журнал решений по профилям. Управление ролями пользователей, блокировки аккаунтов и модерация отзывов ещё не реализованы. Каталог пока ограничен первыми 100 опубликованными профилями.
- Для файлов, каталога, отзывов, загрузки исполнителей, финансового учёта, уведомлений, административной сводки, административного аудита, защищённой сдачи результата, отзыва назначений и разграничения финансовых данных необходимо применить все миграции `0001`–`0018` строго по порядку; без них соответствующие функции не будут работать.
- Загрузка файлов требует `SUPABASE_SERVICE_ROLE_KEY` в серверном окружении. Без него API вернёт HTTP 503 и не выполнит загрузку. Секрет нельзя помещать в клиентский код, GitHub или переменные с префиксом `NEXT_PUBLIC_`.
- Миграция 0014 закрывает прямую загрузку в Storage для обычных authenticated JWT, а регистрацию метаданных переносит в `register_order_file()`. Не удаляйте эти ограничения и не добавляйте публичную INSERT-политику для bucket `order-files`.
- Финансовый раздел ведёт внутренние начисления по завершённым заказам. Платёжный провайдер, эквайринг, банковские операции, вывод средств и подтверждение фактических платежей не подключены; записи ledger не означают, что деньги реально получены или выплачены.
- Уведомления пока только внутри рабочего пространства: email, push, realtime и пользовательские настройки уведомлений ещё не подключены. Rate limiting и автоматизированные интеграционные тесты отсутствуют.
- Перед production обязательны применение миграций в тестовом Supabase-проекте, проверка всех RLS/RPC сценариев под каждой ролью и security review.

## Управление загрузкой исполнителей (v0.8.0)

Примените миграцию `supabase/migrations/0007_provider_capacity.sql` после миграций 0001–0006. В профиле исполнителя/агентства можно задать лимит активных заказов (1–100). При назначении система проверяет опубликованный профиль, доступность, соответствие специализации заказу и текущую загрузку. Активными считаются заказы в статусах `REVIEW`, `IN_PROGRESS` и `QA`; завершённые и отменённые не занимают лимит. В каталоге отображается только агрегированное число активных заказов и лимит.


## Финансовый контур (v0.9.0)

Примените `supabase/migrations/0008_financial_ledger.sql` после 0001–0007. Ответственное агентство или администратор задаёт стоимость для клиента, назначенного исполнителя и его выплату, а также комиссию SELLFORM (0–30%). Остаток после комиссии и выплаты учитывается как доход агентства. После статуса `COMPLETED` ответственное агентство формирует проводки: начисление клиенту, доход агентства, обязательство перед исполнителем и комиссию платформы. Операция идемпотентна, а условия блокируются после создания проводок. Раздел `/finance` показывает доступную пользователю историю начислений. Это внутренний управленческий учёт, не платёжная система.


## Уведомления (v1.0.0)

Примените `supabase/migrations/0009_notifications.sql` после `0008_financial_ledger.sql`. События создаются на стороне PostgreSQL при новой заявке, смене статуса, назначении исполнителя, загрузке файла, отзыве и финансовом начислении. Пользователь видит только собственные уведомления в `/workspace`; можно отметить одно или все уведомления прочитанными. Дедупликация обеспечивается уникальным ключом события. Это внутренняя лента, не email- или push-рассылка.


## Административный доступ

При регистрации пользователь выбирает `SELLER`, `AGENCY` или `FREELANCER`; серверный триггер принимает только эти три значения. Повышение до `ADMIN` выполняет только владелец проекта через доверенный Supabase SQL Editor после проверки личности пользователя. Не добавляйте публичную регистрацию администраторов и не выдавайте эту роль через клиентский интерфейс. Для страницы `/admin` требуются миграции `0010_admin_dashboard.sql`, `0011_provider_moderation.sql` и `0012_role_aware_registration.sql`. Для просмотра администратором файлов и истории заказов дополнительно нужна миграция `0013_admin_order_audit_access.sql`.


## Модерация каталога (v1.2.0)

Примените `supabase/migrations/0011_provider_moderation.sql` после миграции 0010. Новые профили, запрашивающие публикацию, получают статус `PENDING` и появляются в очереди администратора `/admin`. Администратор может одобрить профиль или отклонить его с обязательной причиной. Отклонённый профиль снимается с публикации; владелец может исправить данные и отправить его повторно. Изменение описания, специализаций, портфолио, цен или валюты у одобренного профиля автоматически возвращает его на проверку. Публичный каталог и назначение на заказ дополнительно защищены проверкой статуса на уровне PostgreSQL. Профили, которые были опубликованы до этой миграции, сохраняют статус `APPROVED` для обратной совместимости.


## Регистрация B2B-участников (v1.3.0)

Примените `supabase/migrations/0012_role_aware_registration.sql` после миграции 0011. На `/login` можно создать аккаунт селлера, агентства или независимого исполнителя. Тип роли проверяется серверным триггером PostgreSQL; подмена значения на `ADMIN` или произвольную роль приводит к созданию обычного аккаунта SELLER. Уже существующие профили и их роли не меняются.
## Административный просмотр материалов заказа (v1.5.0)

Примените `supabase/migrations/0013_admin_order_audit_access.sql` после миграции 0012. Администратор получает доступ только на чтение к метаданным вложений и истории статусов всех заказов. Это устраняет ситуацию, когда администратор мог открыть заказ, но не мог просмотреть его файлы или историю. Права участников и запрет прямого изменения истории статусов не расширяются.

## Сдача результата (v1.6.0)

В карточке заказа участники выбирают тип вложения: техническое задание, исходный материал или готовый результат. Только ответственный селлер/агентство/ADMIN либо назначенный исполнитель может загрузить соответствующий тип. Переход в QA требует свежий файл `DELIVERABLE`, созданный после последнего перевода заказа в `IN_PROGRESS`. Если селлер возвращает результат на доработку, исполнитель должен загрузить новую версию; предыдущий файл остаётся в истории.

Партнёрское агентство и независимый исполнитель могут отправить на QA только заказ, назначенный их аккаунту. Партнёрское агентство не получает права управлять чужой основной очередью или назначать исполнителей в заказ.

## Диагностика deployment

После публикации откройте `/api/health`:
- HTTP 200 и `status: "ok"` — публичная конфигурация Supabase и серверный Storage secret присутствуют.
- HTTP 200 и `status: "partial"` — приложение отвечает, но `SUPABASE_SERVICE_ROLE_KEY` отсутствует; файловый API вернёт HTTP 503 при загрузке.
- HTTP 503 и `status: "not_configured"` — добавьте `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` и повторите deployment.

Endpoint не проверяет подключение к PostgreSQL и применение миграций.

## Защита API-маршрутов (v1.8.0)

Все динамические API-маршруты заказов проверяют UUID заказа и, где применимо, UUID файла до обращения к базе. Некорректные идентификаторы отклоняются с HTTP 400. Схемы назначения исполнителей, смены статуса и отзывов отклоняют неизвестные поля; суммы назначения ограничены диапазоном NUMERIC(12,2) и двумя знаками после запятой. Эти проверки дополняют, но не заменяют Supabase RLS и проверки полномочий в RPC.

Страница `/settings` позволяет владельцу аккаунта изменить имя контактного лица и название компании/бренда, посмотреть email и тип кабинета, а также завершить сессию. API `GET/PATCH /api/profile` проверяет текущую Supabase-сессию; PATCH принимает только `full_name` и `company_name`. Поля `role`, `id` и права аккаунта не принимаются от браузера. Используются существующие политики RLS и column-level grants миграции `0003_security_and_rpc.sql`; отдельная миграция для версии 1.7.0 не нужна.


## Назначения исполнителей (v1.9.0)

В карточке заказа уже назначенные исполнители не предлагаются повторно в списке новых назначений. Список текущих назначений отображает имя или название компании, тип участия, согласованную сумму и дату назначения. API возвращает безопасные сообщения об ошибках вместо сырых сообщений PostgreSQL; технический код ошибки сохраняется только в серверном журнале. Эти улучшения используют существующую RPC `assign_order_provider()` и не требуют новой SQL-миграции.

### Assignment revocation (v2.0.0)

Apply `supabase/migrations/0015_assignment_revocation_and_access.sql` after migration 0014. This migration preserves assignment history and removes revoked providers from order, file metadata, private Storage download, and workflow authorization. The responsible agency or an administrator can revoke an active assignment from the order page; assigning that provider again creates a new history row. Do not deploy the new UI/API before applying the migration, because the endpoint depends on `revoke_order_provider` and the `order_assignments.status` column.

### API error handling (v2.1.0)

API handlers translate known Supabase/PostgreSQL error codes into stable public HTTP responses. Raw database messages are kept out of client responses; unknown failures return a generic message and should be investigated through server logs. This does not replace Supabase RLS or the authorization checks in database RPC functions.


## Защита финансовых данных (v2.2.0)

Примените `supabase/migrations/0016_finance_visibility_and_settlement_hardening.sql` после миграции 0015. Полная разбивка финансовых условий заказа доступна только селлеру-владельцу заказа, ответственному агентству и администратору. Исполнитель получает только собственные проводки из `finance_ledger` по `beneficiary_id`; он не получает сумму клиента, комиссию и доход агентства из таблицы финансовых условий. RPC `settle_completed_order()` дополнительно ограничена ролью ответственного агентства/администратора и использует пустой `search_path`.

В API загрузки файлов убрана выдача сырых сообщений Supabase Storage/PostgreSQL клиенту: технические ошибки журналируются на сервере, клиент получает стабильное нейтральное сообщение.


## Лимиты исполнителей и актуальные назначения (v2.3.0)

Примените `supabase/migrations/0017_active_provider_capacity_and_finance.sql` после миграции 0016. Назначение фрилансера или партнёрского агентства снова проверяет опубликованный профиль, доступность, специализацию и лимит активных заказов. Проверка выполняется внутри транзакции с блокировкой строки профиля исполнителя, поэтому параллельные назначения не должны обходить лимит. В расчёт входят только назначения со статусом `ACTIVE` и заказы в `REVIEW`, `IN_PROGRESS` или `QA`; отозванные назначения не занимают лимит. Финансовые условия теперь могут ссылаться только на исполнителя с активным назначением на этот заказ. Это внутренний учёт: реальное списание или перевод денег не выполняется.


## Безопасность SECURITY DEFINER (v2.4.0)

Примените `supabase/migrations/0018_security_definer_search_path_hardening.sql` после миграции 0017. Она фиксирует пустой `search_path` для всех SECURITY DEFINER RPC и trigger-функций, чтобы объекты из пользовательских схем не могли подменять разрешение имён. PostgreSQL продолжает находить встроенные функции через `pg_catalog`; ссылки на таблицы и функции приложения квалифицированы схемой. Перед применением сделайте резервную копию и проверьте историю миграций.
